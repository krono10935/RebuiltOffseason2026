## Architecture
- Each mechanism follows the AdvantageKit IO pattern: `XSubsystem` → `XIO` interface → real implementation (`XIOCTRE` / `XIOReal` / `XIORev`) + `XIOSim`.
- Hardware (motors, sensors, cameras) is touched ONLY inside IO implementations. Subsystems read `inputs` and must call `Logger.processInputs(...)` once per loop.
- Real vs sim IO is picked with `RobotBase.isReal()` or `Constants.currentMode`; both paths must be selected consistently.
- `frc.lib` holds shared code (state machine, math, field utils, `VirtualSubSystem`). A change there affects every subsystem.
- `SuperStructure` (built on `StateMachine`) coordinates the mechanisms and wires subsystems, commands and controller bindings. `RobotContainer` only instantiates the subsystems and sets up autos.
- `BuildConstants.java` is generated by gversion at build time — not hand-written.

## Command semantics — use these exactly, don't guess

| Method | Group type | Ends when |
| --- | --- | --- |
| `alongWith()` | `ParallelCommandGroup` | **ALL** commands finish |
| `raceWith()` | `ParallelRaceGroup` | **ANY** command finishes |
| `deadlineFor()` | `ParallelDeadlineGroup` | the calling (deadline) command finishes; the others are interrupted |
| `andThen()` | `SequentialCommandGroup` | the last command finishes |

| Factory | Behavior |
| --- | --- |
| `runOnce()` / `InstantCommand` | runs once, finishes immediately |
| `run()` / `RunCommand` | runs every loop, **never finishes on its own** |
| `runEnd()` | runs every loop, end action on interrupt, **never finishes on its own** |
| `startEnd()` | start action once, end action on interrupt, **never finishes on its own** |

A never-ending command inside `andThen()` blocks everything after it, and inside `alongWith()` it keeps the whole group alive forever.

## Review focus: logic bugs
We care about logic bugs: code that does the wrong thing no matter what the constants are set to. Constant values are not reviewed (see the last section).

## Logic bugs that matter most here (report these first)
- Unit mistakes: Phoenix 6 works in rotations and rotations/sec, WPILib geometry in meters/radians. Watch rotations↔radians, gear ratios applied twice (or not at all) when `SensorToMechanismRatio` is set, degrees passed where radians are expected.
- State machine / `SuperStructure` logic: unreachable states, missing or wrong transitions, states that can't be exited, two mechanisms commanded into conflicting states.
- Command lifecycle: a command that never ends where it must (sequences, autos), one that ends immediately where it should hold, missing `addRequirements(...)`, conflicting default commands, stop/cleanup actions removed from `end()` / `runEnd()`.
- Wrong comparisons and conditions: inverted checks, `==` on doubles instead of a tolerance (`IsNear`), off-by-one, wrong sign, wrong variable used.
- Hardcoded overrides and disabled logic: sensor values stubbed to a fixed value (e.g. `hasPiece = true`), commented-out periodic calculations or safety checks that other code still relies on.
- Anything that blocks or is slow inside `periodic()` or a command's `execute()` (20 ms loop): sleeps, waits, file/network I/O, configuring motors every loop.
- CTRE `StatusSignal`s that are stored and reused must be refreshed (`refresh()` / `BaseStatusSignal.refreshAll`) before reading, or they silently return old data.
- Red-alliance handling: poses, paths and targets that must be flipped with `AllianceFlipUtil` / PathPlanner flipping but aren't (or are flipped twice).
- Sim IO that diverges from real IO in behavior (different units, sign, or limits) so sim tests prove nothing.
- Mechanisms with a range of motion (intake pivot, hood) that can be commanded past their limits — missing soft limits or clamping.
- Swerve: module order mismatches between kinematics, modules and odometry; gyro sign/direction errors; odometry not updated every loop.
- Shooting math (`ShotCalculator`, `ShootCalculatorWithMovement`): wrong frames (robot vs field), wrong sign for robot velocity compensation, divide-by-zero / NaN cases.
- Cross-subsystem impact: changes to shared code (`frc.lib`, `SuperStructure`, `RobotContainer`, `UnitConversions`) that break callers in other subsystems; public methods renamed or removed while still called elsewhere.

## Known and intentional — do not report
- Constant VALUES are placeholders until the robot is built and tuned: CAN IDs (including duplicate/colliding IDs), PID/feedforward gains, gear ratios, limits, setpoints, current limits, inversions, sim constants — anything in a `*Constants` file. Don't report them.
- DO report logic that uses a constant wrongly: the wrong constant referenced, wrong units, a ratio applied twice, a limit that is defined but never enforced.
- PathPlanner `.path` / `.auto` files under `src/main/deploy` are edited in the PathPlanner GUI, not by hand.
- Named commands and event markers used by the autos are not implemented yet — don't report that they aren't registered.
- Style, naming, missing Javadoc, function length, magic numbers, and refactor suggestions — don't report. Correctness only.
